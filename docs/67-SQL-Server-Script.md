# سكربت قاعدة البيانات على SQL Server (المرحلة 5أ)

**الفكرة:** أول مراحل الخطة 5 (`docs/51-Plan-Opening-Warehouses-Treasury-Reps-SQL-Web.md`): نقل البيانات إلى SQL Server.

في هذه المرحلة يكتب المولّد ملفًا واحدًا: **`dist/sql/RetailStore_Schema.sql`**. يبني قاعدة البرنامج كاملة على SQL Server من نفس تعريف الجداول (`tools/schema.py`) الذي يبني منه `BuildSchema` ملف Access.

- **لا يتغير البرنامج نفسه بعد.**
- **نقل البيانات وربط Access بالخادم في 5ب**، وتعديل الكود في 5ج.
- **هذه المرحلة لا تحتاج قرار مكان الخادم.** السكربت واحد للمحل وللسحابة.

## 1) ما في السكربت
**سكربت واحد للإنشاء والترقية.** مثل `BuildSchema`، كل أمر يتحقق أولًا مما هو موجود، فيُشغَّل مرة أولى على قاعدة فارغة، ثم مرة بعد كل تحديث للبرنامج. لا يحذف بيانات.

| # | الجزء | التفاصيل |
|---|---|---|
| 1 | **الجداول** | الجداول الناقصة (90 جدولًا) بأعمدتها، والمفتاح الأساسي، والقيم الافتراضية |
| 2 | **الأعمدة الناقصة** | لجدول موجود: يضيف كل عمود جديد بقيمته الافتراضية، مثل ترقية Access |
| 3 | **الشروط (CHECK)** | قواعد التحقق نفسها التي في Access، مثل «المبلغ لا يكون سالبًا» و«الحالة من القائمة». تُحذف وتُنشأ في كل تشغيل، فيسري الشرط الذي خففه تحديث |
| 4 | **الفهارس** | الفهارس والفريدة منها. والفهارس التي أزالها البرنامج تُحذف |
| 5 | **البيانات الأولية** | الجدول الفارغ يأخذ كل بياناته الأولية: الإعدادات، والأدوار، والصلاحيات، والشاشات، والحسابات، والعملات، والوحدات... وجداول الترقيم والصلاحيات والحسابات تأخذ الصفوف الجديدة فقط. والصلاحية الجديدة تُعطى لأدوارها، كما في Access |
| 6 | **الأسماء الإنجليزية** | للصفوف الأساسية، إن كانت فارغة |
| 7 | **العلاقات** | 210 علاقة بالحذف والتحديث المتتالي نفسه، بعد البيانات. العلاقات التي لا يفرضها البرنامج تُحذف إن وُجدت |

## 2) الأنواع
| Access | SQL Server | لماذا |
|---|---|---|
| ترقيم تلقائي | `INT IDENTITY` | تُحفظ الأرقام نفسها عند النقل (5ب) |
| رقم طويل / صحيح / بايت | `INT` / `SMALLINT` / `TINYINT` | |
| عملة (المبالغ والكميات والنسب) | `MONEY` | **نفس نوع Access:** 4 خانات عشرية، ويعود لـ Access «عملة» عند الربط |
| تاريخ / تاريخ ووقت | `DATETIME` | يعود لـ Access «تاريخ/وقت» مع كل برامج تشغيل ODBC |
| نعم/لا | `BIT NOT NULL` | |
| نص قصير / طويل | `NVARCHAR(n)` / `NVARCHAR(MAX)` | Unicode للعربي |

**تغيير عن الخطة:** كانت الخطة تقول `DECIMAL(19,4)` و`DATETIME2`. اخترت `MONEY` و`DATETIME` لأن Access يربطهما بنفس أنواعه تمامًا:
- `DECIMAL` يصير في Access «عشري»، وله مشكلات معروفة في الترتيب والمجاميع.
- `DATETIME2` يظهر نصًا مع برنامج تشغيل ODBC القديم.

**عمود `RowVer` (ROWVERSION) في كل جدول:** Access يستعمله ليعرف هل تغيّر السجل عند الحفظ. بدونه تظهر رسالة «تعارض في الكتابة» (Write Conflict) مع الجداول التي فيها أعمدة نعم/لا أو مبالغ. لا يكتب فيه البرنامج.

**اختلافان عن Access، عالجهما المولّد:**
- **الفهرس الفريد على حقل يقبل الفراغ:** Access يقبل أكثر من سجل فارغ فيه، وSQL Server سجلًا واحدًا. فالفهرس يشمل القيم المكتوبة فقط (`WHERE ... IS NOT NULL`)، مثل الباركود.
- **التواريخ في البيانات الأولية** تُكتب `yyyymmdd`، فيقرؤها الخادم بالطريقة نفسها أيًّا كانت لغته.

## 3) التشغيل (على جهازك أو الخادم)
1. ثبّت **SQL Server Express** (مجاني) و**SQL Server Management Studio**.
2. أنشئ القاعدة مرة واحدة، بترتيب عربي لا يفرّق بين الحروف الكبيرة والصغيرة، مثل Access:
   ```sql
   CREATE DATABASE RetailStore COLLATE Arabic_100_CI_AS;
   ```
3. افتح `dist\sql\RetailStore_Schema.sql` في Management Studio، واختر القاعدة `RetailStore`، ثم Execute. أو من سطر الأوامر:
   ```
   sqlcmd -S .\SQLEXPRESS -d RetailStore -E -f 65001 -i RetailStore_Schema.sql
   ```
   الملف بترميز UTF-8 مع BOM، فيقرأ البرنامجان العربي صحيحًا.
4. في الآخر تظهر رسالة: `RetailStore schema: done (90 tables, ...)`.
5. **شغّله مرة ثانية:** يجب أن ينتهي بلا أخطاء ولا تغيير، وهذا اختبار الترقية.

**بعد كل تحديث للبرنامج:** شغّل السكربت الجديد على القاعدة نفسها. يضيف الجداول والأعمدة والفهارس والعلاقات والصلاحيات الجديدة.

## 4) للمطوّر
| الملف | ما فيه |
|---|---|
| `tools/gen_sql.py` (جديد) | `build_sql`؛ الأنواع `SQL_TYPES`؛ ترجمة القيم الافتراضية `default_sql`؛ ترجمة قواعد Access إلى CHECK (`field_rule_sql`، `table_rule_sql`): `Between`، و`In`، و`Like` (`#` = رقم)، و`Is Null`، و`And` / `Or`؛ `cascade_conflicts` |
| `tools/generate.py` | يكتب `dist/sql/RetailStore_Schema.sql` (UTF-8 مع BOM، CRLF) |
| `requirements-dev.txt` | `sqlglot` (اختياري): قراءة الأوامر كـ T-SQL في الاختبارات |

**`cascade_conflicts`:** SQL Server يرفض جدولًا يصله الحذف المتتالي من جدول واحد بطريقين، أو دورة حذف (الخطأ 1785)، وAccess يقبلهما. المولّد يتوقف إن ظهر ذلك في تعريف الجداول، والاختبار يتأكد أنه لا يوجد.

**القاعدة الجديدة:** كل جدول أو حقل أو قاعدة جديدة في `tools/schema.py` يصل إلى السكربت تلقائيًا بـ `tools/generate.py`. لا يُعدَّل السكربت يدويًا.

## 5) الاختبارات (`tests/test_sql_server.py`)
SQL Server غير متاح في بيئة التطوير، لذلك يُختبر السكربت بثلاث طرق:

1. **كنص:**
   - كل جدول وعمود ومفتاح وقاعدة وفهرس وعلاقة وصف أولي موجود؛
   - الأنواع والقيم الافتراضية وترجمة القواعد صحيحة؛
   - كل أمر محمي بفحص قبله، فيُعاد تشغيل السكربت بلا خطأ؛
   - العلاقات بعد البيانات؛
   - لا تعارض في الحذف المتتالي؛
   - كل علاقة تشير إلى مفتاح أو فهرس فريد؛
   - الملف محدَّث.
2. **كـ T-SQL** (بـ `sqlglot`): كل أمر إنشاء جدول وقاعدة وفهرس وعلاقة وإدخال صحيح الصياغة.
3. **بالتشغيل:** الجداول والقواعد والقيم الافتراضية والعلاقات تُنشأ في SQLite من نفس الأجزاء المولَّدة، ثم تُدخل البيانات الأولية. كل صف يحقق القواعد والعلاقات، والقيمة الافتراضية تعمل، والقيمة الخاطئة تُرفض.

**لم يُختبر بعد:** التشغيل الفعلي على SQL Server. هذا على جهازك (القسم 3)، وأحتاج رسالة الخطأ إن ظهرت.
