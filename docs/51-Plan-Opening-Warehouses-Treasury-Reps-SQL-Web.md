# خطة: أرصدة أول المدة، والمخازن، والخزائن، والمندوبين، وSQL Server، والويب والتطبيقات

**طلب صاحب المشروع:** ست خطط:
1. أرصدة أول المدة لكل شيء، وعرض رصيد أول المدة لكل سنة أو فترة مالية.
2. أكثر من مخزن، وحركات الصرف والاستلام بينها وإلى جهات أخرى، وكارت الصنف.
3. أكثر من خزينة، والتحويل بينها، ويومية كل صندوق.
4. قسم للمندوبين حسب أنظمة ERP الحديثة: الطلبيات، والتوزيع، والبيع من مخزن السيارة.
5. تحويل قاعدة البيانات إلى SQL Server.
6. تحويل البرنامج إلى ويب (ASP.NET Razor) يعمل على Android وiOS، مع وحدة APIs للتطبيقات.

هذا الملف يدرس كل خطة: ما الموجود الآن في البرنامج، وما الناقص، والتصميم المقترح، والمراحل. ثم يرتب الخطط حسب الأولوية. كل مرحلة تُنفَّذ وحدها، ثم ننتظر الموافقة قبل التالية. يُحدَّث الملف مع التنفيذ.

## خطة 1: أرصدة أول المدة والسنة المالية
### الموجود الآن
| الرصيد | أين | قيده |
|---|---|---|
| الصناديق | شاشة الصناديق: الرصيد **وتاريخه** | الصندوق مدين، و3900 «أرصدة افتتاحية» دائن |
| البنوك | شاشة البنوك: الرصيد وتاريخه | البنك و3900 |
| العملاء والموردون | حقل «الرصيد الافتتاحي» في بطاقة العميل أو المورد | 1300 أو 2100 مقابل 3900، **بتاريخ إنشاء البطاقة** |
| الأصناف | المخزون ← حركة «رصيد افتتاحي»: مرة واحدة لكل صنف، قبل أي حركة، بكمية وتكلفة | 1400 مدين، و3900 دائن |
| الأصول الثابتة | الأصل بمصدر «رصيد افتتاحي» وإهلاكه السابق | |
| باقي الحسابات (رأس المال، والقروض، والمستحقات…) | **قيد يدوي** مقابل 3900 | |
| السنة المالية | إقفال السنة: الإيرادات والمصروفات في 31 ديسمبر إلى الأرباح المحتجزة 3300 | |
| رصيد أول المدة في التقارير | كشف الحساب، ودفتر الأستاذ، وميزان المراجعة، وكشف العميل والمورد، وحركة المنتج، وحركة الخزينة: **رصيد أول المدة = مجموع كل ما قبل بداية الفترة** | |

**المبدأ المستعمل، ويبقى:** رصيد أول أي فترة يُحسب دائمًا من الحركات التي قبلها، ولا يُنسخ رقمه من سنة لسنة. لذلك يبقى صحيحًا دائمًا، حتى لو صُحّح مستند قديم في فترة غير مقفلة. أول السنة الجديدة لا يحتاج «ترحيل أرصدة»، إلا إقفال الإيرادات والمصروفات في الأرباح المحتجزة، وهو موجود.

### الناقص
1. **لا يوجد تاريخ بدء موحّد.** رصيد العميل والمورد يأخذ تاريخ إنشاء البطاقة، فعميل أُضيف بعد شهر من التشغيل يظهر رصيده الافتتاحي في منتصف الفترة.
2. **لا توجد شاشة واحدة لأرصدة البداية.** كل نوع في شاشته، وباقي الحسابات بقيد يدوي. لا شيء يتأكد أن 3900 أصبح صفرًا، أي أن الأرصدة المدخلة متوازنة.
3. **رصيد العميل والمورد مبلغ واحد،** فلا تعرف أعمار الديون من أي فاتورة جاء الرصيد ولا متى يستحق.
4. **رصيد الأصناف يُدخل صنفًا صنفًا،** ولا يوجد إدخال جماعي أو استيراد من Excel.
5. **السنة المالية تبدأ في يناير دائمًا،** ولا يوجد تقرير «أرصدة أول السنة» لكل الحسابات والعملاء والموردين والصناديق والمخزون في صفحة واحدة.

### التصميم المقترح
| العنصر | التصميم |
|---|---|
| **تاريخ بدء التشغيل** | `Settings.OpeningDate`: كل الأرصدة الافتتاحية بهذا التاريخ. لا يكون بعد أول مستند، ولا في فترة مقفلة |
| **شاشة «أرصدة بداية التشغيل»** | خطوات بالترتيب: الحسابات العامة (جدول: الحساب، مدين، دائن)، ثم العملاء، ثم الموردون، ثم الصناديق والبنوك، ثم المخزون. في الأعلى **رصيد حساب «إجمالي الأرصدة الافتتاحية» (3900)** وتفصيله حسب المصدر، وتنبيه إن لم يكن صفرًا |
| **رصيد العميل والمورد** | مبلغ واحد لكل منهما، في جدول واحد لكل العملاء أو الموردين، بتاريخ بدء التشغيل |
| **رصيد المخزون الجماعي** | جدول بكل الأصناف: الكمية والتكلفة، مع **استيراد من Excel**. بعد خطة 2 يصبح لكل مخزن |
| **الفترات المالية** | جدول `FiscalPeriods` وشاشة يضيف فيها المحاسب كل سنة أو فترة مالية: الاسم، والبداية، والنهاية. الفترة الجديدة تبدأ في اليوم التالي لنهاية السابقة، فلا تداخل ولا فجوة. الإقفال، والفترات السريعة «هذه السنة / السنة الماضية»، والقوائم المالية تتبع الفترات |
| **تقرير «أرصدة أول المدة»** | لأي تاريخ (أول سنة أو أول فترة) في تقرير واحد بأقسام: ميزان الحسابات، والعملاء، والموردون، والصناديق، والبنوك، والمخزون بالكمية والقيمة. محسوب من الحركات |
| **الميزانية الافتتاحية** | طباعة قائمة المركز المالي في أول السنة. تعمل الآن بتاريخ؛ يُضاف زر مباشر في شاشة إقفال السنة |

### قرارات صاحب المشروع
| القرار | الاختيار |

## خطة 3: الخزائن والتحويل ويومية الصندوق
### الموجود الآن (`docs/17-Treasury.md`)
- **صناديق متعددة:** خزينة رئيسية وصناديق كاشير، لكل منها رصيد افتتاحي، ولكل صندوق حساب في الشجرة (110000 + رقمه).
- **سندات النقدية:** قبض، وصرف، و**تحويل بين الصناديق**. الصرف والتحويل يُرفضان إن زادا عن الرصيد.
- **تصفية يومية الكاشير:** الدفتري والفعلي والفرق والترحيل للخزينة.
- **صندوق المستخدم:** لكل موظف صندوقه (`Employees.CashBoxID`)، والكاشير يصفّي صندوقه فقط.
- **التقارير:**
  - «حركة الخزينة (تفصيلي)»: رصيد أول المدة، ثم كل حركة، ثم الرصيد؛
  - «حركة الخزينة اليومية»: لكل يوم رصيد أول اليوم، والمقبوضات، والمدفوعات، ورصيد آخر اليوم، **مجاميع فقط**؛
  - «أرصدة الخزينة والصناديق».

### الناقص
1. **«يومية الصندوق» بالتفصيل في صفحة لكل يوم:**
   - رصيد أول اليوم؛
   - المقبوضات بالتفصيل (مبيعات نقدية، وتحصيل من عميل، وسند قبض، وتحويل وارد) مع إجماليها؛
   - المصروفات بالتفصيل (مرتجع، ودفع لمورد، ومصروف، وسند صرف، وتحويل صادر) مع إجماليها؛
   - رصيد آخر اليوم، والتصفية إن وُجدت.

   التقارير الحالية تعطي إما التفاصيل لفترة كاملة، أو المجاميع لكل يوم.
2. **أمين الصندوق:** صندوق يتبع أكثر من مستخدم، ومنع المستخدم من الصرف من صندوق غيره.
3. **استلام التحويل** (اختياري): التحويل يبقى «بالطريق» حتى يؤكده أمين الصندوق المستلم. يمنع الخلاف عند تسليم النقدية.
4. **نوع صندوق «عهدة مندوب»:** تحتاجه خطة 4.

### المراحل
| # | المرحلة |
|---|---|
| 3أ | تقرير يومية الصندوق التفصيلي (صفحة لكل يوم ولكل صندوق) من مركز التقارير ومن شاشة الخزينة |
| 3ب | أمناء الصندوق والصلاحية على كل صندوق، والتحويل بانتظار الاستلام، ونوع صندوق العهدة |

## خطة 2: المخازن المتعددة وحركات الصرف والاستلام وكارت الصنف
### الموجود الآن
- **مخزن واحد:** رصيد كل صنف = مجموع حركاته (`InventoryTransactions`). البيع والشراء والمرتجعات والجرد والحركات اليدوية تكتب فيه.
- **الحركات اليدوية:** رصيد افتتاحي، وإضافة، وخصم تالف. **بلا جهة:** لا يُعرف لمن صُرف الصنف أو من أين جاء.
- **التكلفة:** متوسط مرجّح واحد لكل صنف (`Products.AverageCost`).
- **تقرير «حركة منتج»:** رصيد أول المدة، ثم الحركات، ثم الرصيد التراكمي. **بالكمية فقط.**

### التصميم المقترح
| العنصر | التصميم |
|---|---|
| **المخازن** (`Warehouses`) | الكود، والاسم، والنوع: رئيسي، أو فرع، أو **سيارة مندوب**، أو تحت التشغيل. أمين المخزن، ومركز التكلفة، ونشط. المخزن الحالي يصبح «المخزن الرئيسي» رقم 1، وكل الحركات القديمة له |
| **كل حركة مخزون** | تحمل المخزن (`InventoryTransactions.WarehouseID`). الرصيد = مجموع الحركات **لكل صنف في كل مخزن**، و`CurrentQuantity` يبقى إجمالي كل المخازن |
| **المستندات** | فاتورة البيع ومرتجعها، والشراء ومرتجعه، والجرد: كل مستند يحمل مخزنه. الافتراضي مخزن الجهاز أو المستخدم (نقطة البيع لا تسأل) |
| **الجهات** (`StockParties`) | جهات الصرف والاستلام غير العملاء والموردين: **قسم**، و**صالة إنتاج**، و**هالك**، وأخرى. لكل جهة حساب مصروفها أو حساب تحت التشغيل |
| **سند مخزني** (`StockDocuments` + `StockDocumentLines`) | النوع: **صرف**، أو **استلام**، أو **تحويل بين مخزنين**. للصرف والاستلام جهة: عميل، أو مورد، أو قسم، أو صالة إنتاج، أو هالك. المسودة لا تحرك المخزون، و«الترحيل» يحركه، ثم «إلغاء الترحيل» |
| **التحويل بين المخازن** | يخصم من المخزن المرسِل ويضيف للمستلم بنفس التكلفة، بلا ربح ولا خسارة. خيار «بالطريق» حتى يؤكد المستلم |
| **القيود** | التحويل: لا قيد إن كان المخزون حسابًا واحدًا، أو من حساب مخزن لآخر إن كان لكل مخزن حساب. الصرف لقسم: مصروف القسم مدين، والمخزون دائن. لصالة إنتاج: تحت التشغيل. للهالك: حساب جديد «هالك المخزون» تحت المصروفات. الاستلام عكس ذلك |
| **كارت الصنف** | لصنف ومخزن (أو كل المخازن) وفترة: **رصيد أول المدة** (كمية وقيمة)، ثم كل حركة (التاريخ، والمستند، والنوع، والجهة، والوارد، والمنصرف، والرصيد، والتكلفة)، ثم **الرصيد النهائي** أو الحالي. يُطبع، ويُفتح من شاشة المنتج |
| **تقارير** | أرصدة الأصناف لكل مخزن، وتقييم المخزون لكل مخزن، والجرد لمخزن محدد، والتحويلات بالطريق |

**إذن التسليم وإذن الاستلام** (مرحلة لاحقة، تحتاجها خطة 4):
- الصرف لعميل يصبح **إذن تسليم** يُنشأ منه الفاتورة، فلا يُخصم المخزون مرتين.
- الاستلام من مورد يصبح **إذن استلام** تُنشأ منه فاتورة الشراء.

### المراحل
| # | المرحلة |
|---|---|
| 2أ | جدول المخازن، والمخزن على كل حركة ومستند، ورصيد كل صنف في كل مخزن، ورصيد أول المدة لكل مخزن (يكمل خطة 1ب) |
| 2ب | التحويل بين المخازن (مع «بالطريق» والاستلام) |
| 2ج | الجهات، وسندات الصرف والاستلام للأقسام وصالات الإنتاج والهالك والعملاء والموردين، وقيودها |
| 2د | كارت الصنف بالكمية والقيمة، وتقارير المخازن، والجرد لكل مخزن |
| 2هـ | إذن التسليم وإذن الاستلام مربوطان بالفواتير |

## خطة 4: المندوبين والتوزيع والبيع المباشر (حسب أنظمة ERP)
### الموجود الآن (`docs/37-Sales-Reps.md`)
- المندوب وعملاؤه؛
- نسبة المستندات للمندوب؛
- الأهداف الشهرية؛
- مسير العمولات وقيده وصرفه؛
- تقارير الأداء والتحصيل.

**لا توجد طلبيات، ولا مخزن للمندوب، ولا خط سير.**

### التصميم المقترح
| العنصر | التصميم |
|---|---|
| **طلبية العميل** (`SalesOrders` + `SalesOrderLines`) | يسجلها المندوب أو المكتب. الحالات: مسودة، ثم معتمدة، ثم قيد التجهيز، ثم مُسلَّمة كليًا أو جزئيًا، ثم مفوترة، أو ملغاة. **تحجز الكمية** في المخزن، فلا تُباع لغيرها |
| **التسليم والتوزيع** | من الطلبية يُنشأ **إذن تسليم** من المخزن (خطة 2هـ) ثم الفاتورة. «رحلة توزيع»: طلبيات عدة عملاء على سيارة واحدة، وتُغلق بما سُلّم وما رجع |
| **البيع من السيارة (Van Sales)** | لكل مندوب **مخزن سيارة** (خطة 2) و**صندوق عهدة** (خطة 3) |
| يوم المندوب | 1) **تحميل:** تحويل من المخزن الرئيسي للسيارة. 2) **بيع مباشر:** فاتورة من مخزن السيارة، نقدًا لصندوق العهدة أو آجلًا. 3) **تحصيل** من العملاء لصندوق العهدة. 4) **مرتجعات** من العملاء للسيارة. 5) **تفريغ:** تحويل الباقي للمخزن الرئيسي. 6) **تسوية المندوب:** المتوقع مقابل الفعلي للبضاعة والنقدية، والعجز أو الزيادة، وتسليم النقدية للخزينة |
| **خط السير والزيارات** | أيام زيارة كل عميل، وخطة زيارات يومية، وتسجيل الزيارة ونتيجتها: طلبية، أو بيع، أو تحصيل، أو لا شيء |
| **حدود المندوب** | حد ائتمان وخصم مسموح لكل مندوب، وأسعار خاصة لقائمة أسعار المندوب |
| **التقارير** | رصيد سيارة كل مندوب، وتسوية يومية، والطلبيات المعلّقة، وتنفيذ خط السير، والمبيعات والتحصيل لكل مندوب |
| **تطبيق المندوب** | على الجوال من خلال الـ APIs (خطة 6). **يعمل بلا إنترنت** ثم يزامن: العملاء، والأصناف، ورصيد السيارة، والطلبية، والفاتورة، والتحصيل، والطباعة على طابعة بلوتوث |

## خطة 5: تحويل قاعدة البيانات إلى SQL Server
### الطريقة الموصى بها
- **تبقى واجهة Access كما هي**، وتنتقل البيانات وحدها إلى SQL Server (الإصدار Express المجاني يكفي حتى 10 جيجابايت للقاعدة).
- تتصل الواجهة بالجداول عبر ODBC.
- بذلك يستمر البرنامج يعمل يوم التحويل، وتصبح القاعدة جاهزة لموقع الويب (خطة 6) يعمل على **نفس البيانات** خلال فترة الانتقال.

| الخطوة | التفاصيل |
|---|---|
| **بناء القاعدة** | المولّد يكتب سكربت T-SQL من نفس التعريف `tools/schema.py`: الجداول، والأنواع (`NVARCHAR` للعربي، و`DECIMAL(19,4)` للمبالغ، و`BIT`، و`DATETIME2`)، و`IDENTITY`، والقيم الافتراضية، والقواعد كـ `CHECK`، والعلاقات، والفهارس، والبيانات الأولية. وسكربت ترقية لقاعدة موجودة، مثل `BuildSchema` اليوم |
| **نقل البيانات** | أداة تنقل كل جدول من `RetailStore_BE.accdb` بترتيب العلاقات، مع الحفاظ على الأرقام (`IDENTITY_INSERT`)، ثم تقارن عدد السجلات والمجاميع |
| **الربط** | شاشة «الاتصال بالخادم»: اسم الخادم، والقاعدة، والدخول بحساب Windows أو مستخدم SQL. إعادة ربط كل الجداول بلا DSN، واختبار الاتصال عند فتح البرنامج |
| **تعديل الكود** | `dbSeeChanges` عند فتح الجداول للتعديل، وقراءة رقم السجل الجديد، والمعاملات، والمقارنة بـ True/False، والنسخ الاحتياطي (`BACKUP DATABASE` بدل نسخ الملف)، والجداول المؤقتة تبقى محلية |
| **الأداء** | الاستعلامات الثقيلة، مثل إعادة بناء القيود والتقارير المحاسبية، تُنقل إلى **Views وStored Procedures على الخادم**، فلا تُسحب كل البيانات للجهاز |
| **قاعدة القيود في مكان واحد** | **قرار مهم لخطة 6:** منطق القيود يُنقل إلى الخادم، فيستعمله Access والويب معًا، ولا تختلف القيود بين النظامين |

**الاختبار:** SQL Server غير متاح في بيئة التطوير هنا. تُختبر السكربتات المولَّدة بفحص النص، وتُقارن ترجمة الاستعلامات. **التشغيل الفعلي والقياس على جهازك** على نسخة من بياناتك.

### المراحل
| # | المرحلة |
|---|---|
| 5أ | مولّد سكربت T-SQL للقاعدة والترقية |
| 5ب | أداة نقل البيانات ومطابقتها، وشاشة الاتصال وإعادة الربط |
| 5ج | تعديلات الكود ليعمل على SQL Server، والنسخ الاحتياطي |
| 5د | نقل القيود والتقارير الثقيلة إلى Views وStored Procedures |

## خطة 6: الويب (ASP.NET Core Razor Pages) وAndroid وiOS والـ APIs
### الطريقة الموصى بها
| القرار | الاختيار | السبب |
|---|---|---|
| المنصة | **ASP.NET Core** (الإصدار طويل الدعم): Razor Pages للشاشات، وWeb API للتطبيقات، في حل واحد | طلب صاحب المشروع |
| البيانات | **نفس قاعدة SQL Server** (خطة 5) عبر Entity Framework Core على الجداول الموجودة | Access والويب يعملان معًا أثناء الانتقال |
| منطق العمل | يُكتب بـ C# في طبقة واحدة يستعملها الموقع والـ API. **المواصفات جاهزة:** النسخ المكتوبة بـ Python (`tools/sim.py` و`*_reference.py`) وألف اختبار تصف كل قاعدة. تُنقل الاختبارات نفسها إلى xUnit | لا يُعاد اكتشاف القواعد، والنتيجة تُقارن بنتيجة Access |
| الدخول والصلاحيات | نفس المستخدمين والأدوار والصلاحيات وصلاحيات الشاشات، بكلمات السر نفسها | لا يُعاد إعداد المستخدمين |
| الواجهة | عربية من اليمين لليسار وإنجليزية، **متجاوبة** تعمل على الجوال والتابلت، وقابلة للتثبيت على Android وiOS كتطبيق ويب (PWA) | تطبيق واحد لكل الأجهزة من البداية |
| الـ APIs | REST بإصدار (`/api/v1`)، ودخول بـ JWT، وتوثيق Swagger، وصلاحيات كل عملية، وسجل التدقيق | للتطبيقات وللربط مع أنظمة أخرى |
| التطبيقات الأصلية | لاحقًا وحسب الحاجة: **.NET MAUI** (نفس لغة C#) لتطبيق المندوب، لأنه يحتاج العمل بلا إنترنت وطابعة بلوتوث | |
| الاستضافة | خادم Windows مع IIS في المحل، أو استضافة سحابية، مع HTTPS | يُقرر قبل المرحلة 6أ |
