# التجهيز للتسليم ودليل التثبيت النهائي (المرحلة 7د)

**الهدف (الخطة 7، `docs/51`):** تسليم البرنامج للعميل جاهزًا: الموقع والـ API على الاستضافة، وقاعدة SQL Server، وملف Access المغلق (ACCDE) بسر تفعيل خاص لا يعرفه غير المبرمج، ونقطة البيع وتطبيق المندوب متصلين بالموقع، ومهام المكتب تعمل.

## 1) قرار الاستضافة
**قرار صاحب المشروع:** **استضافة مشتركة (Shared Hosting) على Windows** فيها **SQL Server**، والرفع إليها بحساب **FTP**.

| الجزء | مكانه |
|---|---|
| الموقع (Blazor) والـ API (`/api/v1`) | الاستضافة: IIS بوحدة ASP.NET Core (`AspNetCoreModuleV2`، تشغيل داخل العملية `inprocess`) |
| قاعدة البيانات | SQL Server الاستضافة (قاعدة واحدة، مستخدم SQL له `db_owner` على قاعدته) |
| Access في المكتب | يرتبط بقاعدة الاستضافة عبر الإنترنت (`docs/68`، ODBC Driver 18، `LinkToServer`) |
| نقطة البيع على Windows | الوضع **REMOTE**: عنوان الموقع بـ HTTPS (`docs/83`)، ويعمل بلا إنترنت كما هو |
| تطبيق المندوب | عنوان الموقع بـ HTTPS (`docs/78`) |
| مهام المكتب (القيود والفاتورة الإلكترونية) | **جهاز في المكتب**: Access المختار في «مهام المكتب» (`docs/84`)، أو الخدمة `RetailStore.OfficeService` على ذلك الجهاز (`docs/85`). الاستضافة المشتركة لا تشغّل خدمات Windows |

**ما يعنيه هذا القرار:**
- **لا خادم في المحل:** لا جهاز يعمل ليلًا ونهارًا، ولا عنوان IP ثابت، والموقع يصل إليه المندوب من أي مكان.
- **Access أبطأ قليلًا** لأن القاعدة عبر الإنترنت: يُفضّل للبيع اليومي نقطة البيع على Windows أو الموقع، وAccess للمكتب.
- **النسخ الاحتياطي:** نسخ `BACKUP DATABASE` من شاشة النسخ الاحتياطي (`docs/70`) يكتب الملف على قرص الخادم، وهذا **لا يُتاح في الاستضافة المشتركة** غالبًا. يُستعمل **النسخ الاحتياطي في لوحة تحكم الاستضافة** (يومي، مع تنزيل ملف `.bak` دوريًا).
- **`READ_COMMITTED_SNAPSHOT`:** سكربت القاعدة يشغّله إن سمح المضيف؛ وإن رفض لا يتوقف السكربت بل يطبع تحذيرًا (اطلب من المضيف تشغيله). البرنامج يعمل بدونه، لكن القراءة قد تنتظر حفظ مستخدم آخر.

### ما يُطلب من شركة الاستضافة (قبل التعاقد أو قبل الرفع)
1. **ASP.NET Core على IIS** بوحدة `AspNetCoreModuleV2`، وتطبيق **64 بت**. وجود .NET 10 على الخادم **غير لازم**: النشر الافتراضي «مستقل» (self-contained، نحو 135 ميجابايت). إن كان .NET 10 موجودًا يُنشر بـ `--framework-dependent` (نحو 15 ميجابايت).
2. **WebSockets** مفعّلة (شاشات Blazor تعمل بدونها لكن أبطأ).
3. **شهادة HTTPS** للنطاق (Let's Encrypt المجانية تكفي). **لا يعمل البرنامج على http**: تطبيق المندوب ونقطة البيع يرسلان كلمات المرور.
4. **صلاحية الكتابة** على مجلد `App_Data` في الموقع (مفاتيح الدخول، ومفتاح الـ API إن لم يُكتب، وسجل الأخطاء).
5. **الاتصال البعيد بـ SQL Server** (العنوان والمنفذ) من جهاز المكتب، لـ Access ولخدمة مهام المكتب.
6. **FTP أو FTPS** إلى مجلد الموقع.

## 2) ما أضيف في هذه المرحلة
| الملف | العمل |
|---|---|
| `tools/release.py` | **سر التفعيل الجديد** وحزمة التسليم: `secret` يصنع `release/license-secret.txt` مرة واحدة (48 حرفًا عشوائيًا، **لا يُطبع أبدًا**، ولا يُستبدل)، و`package` يصنع `release/RetailStore/` = `dist/vba` (و`modActivation` فيها بالسر الجديد، مع بقاء ترميز Windows-1256 وCRLF وكل سطر آخر كما هو) و`dist/tools` و`dist/sql` وهذا الدليل، و`code` يحسب كود تفعيل جهاز عميل بالسر الجديد، و`check` يتأكد أن الحزمة بالسر الجديد لا بسر التطوير |
| `dist/tools/MakeAccde.vbs` | يصنع **ملف ACCDE** من الواجهة المبنية (`SysCmd 603` = حفظ باسم > إنشاء ACCDE)، ويرفض الملف المفتوح (وجود `.laccdb`)، ويسأل قبل استبدال ACCDE موجود |
| `tools/deploy_web.py` | **نشر الموقع ورفعه بـ FTP**: `init` (الإعدادات مرة واحدة في `release/web-deploy.json`، ومفتاح توقيع الـ API يُصنع مرة واحدة)، و`publish` (`dotnet publish` لـ Windows x64 مع `appsettings.Production.json`)، و`upload`، و`check` (`/health`)، و`sql` (السكربتان على قاعدة الاستضافة، يحتاج `pip install pymssql`)، و`all` |
| `Program.cs` و`Health.cs` في الموقع | **مفاتيح حماية الدخول** تُحفظ في `App_Data/keys` (`Hosting:KeysFolder`)، فإعادة تشغيل الموقع (الاستضافة المشتركة تعيد تشغيله كثيرًا) لا تُخرج المستخدمين؛ و`Hosting:ForwardedHeaders` خلف وسيط يُنهي HTTPS؛ و**`GET /health`** للتأكد من التثبيت: `{"status":"ok"}` = الموقع يعمل ويقرأ قاعدته، وإلا 503 `{"status":"database"}` بلا تفاصيل (السبب في سجل الموقع) |
| `tools/gen_sql.py` | خيار `READ_COMMITTED_SNAPSHOT` داخل `BEGIN TRY ... END TRY BEGIN CATCH ... END CATCH` |
| `.gitignore` | `release/` و`appsettings.Production.json` لا يدخلان المستودع أبدًا |

**الرفع (`upload`):** يرفع أولًا `app_offline.htm` (صفحة «جاري تحديث البرنامج»: IIS يوقف الموقع ويفك ملفاته)، ثم كل الملفات **عدا `App_Data`** (مفاتيح الخادم وسجله لا تُمس) **وملفات التطوير** (`appsettings.Development.json` و`.pdb` وقواعد SQLite)، ثم يحذف `app_offline.htm`. إن انقطع الرفع تبقى صفحة التحديث، فلا يعمل نصف برنامج: أعد `upload`.

**الأسرار:** كلمة مرور SQL Server ومفتاح الـ API في `release/web-deploy.json` على جهازك فقط، ثم في `appsettings.Production.json` على الاستضافة (IIS لا يعرض هذا الملف: كل الطلبات تذهب إلى البرنامج، والبرنامج لا يقدّم إلا `wwwroot`). **كلمة مرور FTP لا تُحفظ:** تُسأل كل مرة، أو من المتغير `RETAIL_FTP_PASSWORD`. **لا تُرسل أي كلمة مرور في محادثة ولا في بريد.**

## 3) التثبيت النهائي بالترتيب
### أ) على جهاز المبرمج (مرة واحدة، ثم مع كل إصدار)
```bat
python tools\generate.py
python -m unittest discover -s tests
python tools\release.py secret
python tools\release.py package
python tools\release.py check
```
- **انسخ `release\license-secret.txt` في مكان آمن** (فلاشة أو مدير كلمات مرور). بدونه لا يُصنع كود تفعيل جديد، وتغييره يُبطل كل كود أُعطي.
- السر الموجود في المستودع (`src/vba/modActivation.bas`) **سر التطوير**: يبقى كما هو، والحزمة وحدها فيها السر الحقيقي.

### ب) قاعدة البيانات على الاستضافة
1. أنشئ القاعدة ومستخدمها من لوحة تحكم الاستضافة.
2. `python tools\deploy_web.py init` (العنوان، والقاعدة، والمستخدم، وكلمة المرور، وFTP، وعنوان الموقع). الإجابة الخاطئة يُسأل عنها مرة أخرى دون ضياع ما قبلها، وعنوان الموقع بلا `https://` يُكمَّل، و`http://` مرفوض، وEnter يُبقي القيمة السابقة (لتغيير كلمة المرور وحدها أعد `init` واضغط Enter في الباقي).
3. **جرّب الاتصال وحده:** `python tools\deploy_web.py sql-check` يطبع اسم القاعدة وإصدار SQL Server، ثم يفحص **كل صلاحية** يحتاجها السكربتان والبرامج واحدة واحدة (`HAS_PERMS_BY_NAME`): `CREATE TABLE`، و`ALTER` و`REFERENCES` على `dbo` (الأعمدة والقواعد والفهارس والعلاقات ونقل بيانات Access)، و`CREATE VIEW` (العروض الـ 518)، وإنشاء المخطط `[en]` مرة واحدة (`CREATE SCHEMA`) ثم `ALTER` عليه، والقراءة والإضافة والتعديل والحذف. لا يلزم `db_owner`: يكفي `db_ddladmin` مع `db_datareader` و`db_datawriter`، ويذكر الأمر الناقص وحده. إن رُفض الدخول (الخطأ **18456**) فالخادم وصل والعنوان صحيح، والسبب كلمة المرور أو المستخدم أو أن المستخدم غير مُعطى لهذه القاعدة في لوحة التحكم: جرّب البيانات نفسها في SQL Server Management Studio (SQL Server Authentication). والخطأ 4060 = اسم القاعدة؛ وعدم الرد = العنوان أو المنفذ أو الاتصال البعيد غير مسموح.
4. أنشئ الجداول والعروض: `python tools\deploy_web.py sql` (يشغّل `dist\sql\RetailStore_Schema.sql` ثم `dist\sql\RetailStore_Queries.sql`)، أو من شاشة **SQL Server** في Access (`docs/68`)، أو من SQL Server Management Studio.
   إن توقف جزء من السكربت يُذكر الملف ورقم الجزء ورسالة الخادم؛ ما قبله محفوظ، والسكربت يُعاد بأمان.
5. **البيانات الموجودة** (محل يعمل على Access): من شاشة SQL Server في Access: نقل البيانات `TransferAllData` ثم المطابقة `CompareAllData` ثم الربط `LinkToServer` (`docs/68` و`docs/70`). محل جديد: لا نقل، والبيانات الأولية في السكربت.

### ج) الموقع
```bat
python tools\deploy_web.py all
```
- يُنشر ويُرفع ثم يطلب `https://<الموقع>/health` ويطبع «The site runs and reads its database».
- إن ظهرت صفحة **500.30** أو 503: `python tools\deploy_web.py publish --stdout-log` ثم `upload`، واقرأ `App_Data\logs` عبر FTP، ثم انشر مرة أخرى بدون `--stdout-log`.
- أول دخول: `admin` بلا كلمة مرور، ويطلب البرنامج كلمة مرور جديدة **فورًا**.
- صفحة توثيق الـ API (`/api/docs`) مغلقة افتراضيًا في الإنتاج (سؤال `init`).

### د) Access على أجهزة المكتب
1. على جهاز بنفس Access العميل (**32 أو 64 بت كالعميل**): انسخ `release\RetailStore` وشغّل `tools\BuildFrontEnd.vbs` من **داخل الحزمة** (يستورد الوحدات بالسر الجديد)، واختر «end-user mode» = نعم.
2. أغلق الملف، ثم شغّل `tools\MakeAccde.vbs` واختر `RetailStore_FE.accdb`: يخرج `RetailStore_FE.accde`.
3. اربط الواجهة بقاعدة الاستضافة (شاشة SQL Server، `LinkToServer`) قبل `MakeAccde` أو بعده من داخل البرنامج.
4. **سلّم `RetailStore_FE.accde` فقط**، واحتفظ بـ ACCDB عندك: أي تعديل لاحق فيه ثم ACCDE جديد.
5. **التفعيل:** يفتح العميل البرنامج فيظهر **رقم الجهاز** في شاشة التفعيل؛ ترسل له الكود من `python tools\release.py code XXXX-XXXX-XXXX-XXXX`.

### هـ) نقطة البيع على Windows (`docs/83`، `docs/86`)
- انشر `RetailStore.Pos` كما في `docs/83`، ومن **إعدادات القاعدة** اختر **REMOTE** وعنوان الموقع `https://...` ورقم الجهاز (`POS1` ...).

### و) تطبيق المندوب (`docs/78`)
- ابنِ تطبيق Android (`RetailStore.Mobile.slnx`) ووزّعه، وفي أول تشغيل اكتب عنوان الموقع `https://...`.

### ز) مهام المكتب (`docs/84`، `docs/85`)
- **إما** Access على جهاز واحد في المكتب: شاشة «مهام المكتب»، واسم الجهاز في `Settings.OfficeSyncComputer`، ولوحة التحكم مفتوحة.
- **أو** الخدمة `RetailStore.OfficeService` على ذلك الجهاز (بدون Access مفتوح): `dotnet publish` ثم سلسلة الاتصال بقاعدة الاستضافة في `appsettings.json` و`sc.exe create` (`docs/85` القسم 2)، و`--check` للتأكد.
- الموقع ينبّه من له صلاحية `OFFICE_SYNC` إن توقفت المهام.

### ح) الفاتورة الإلكترونية
- التسجيل (onboarding) لدى هيئة الزكاة (`docs/47`) أو منظومة مصر (`docs/48`، `docs/49`) من Access بعد الربط بالقاعدة، ثم الإرسال من مهام المكتب.

## 4) التحديث بعد التسليم
- **الموقع:** `python tools\deploy_web.py all` (نفس `web-deploy.json`، فلا يتغير مفتاح الـ API ولا يخرج أي هاتف أو جهاز).
- **القاعدة:** `python tools\deploy_web.py sql` (السكربتان يُعادان بأمان على قاعدة فيها بيانات، `docs/67`).
- **Access:** `python tools\release.py package` ثم `BuildFrontEnd.vbs` و`MakeAccde.vbs` وتسليم ACCDE الجديد. **السر لا يتغير**، فالأجهزة المفعّلة تبقى مفعّلة.

## 5) الاختبار
- **Python:** `tests/test_delivery.py` (السر يُصنع مرة ولا يُطبع، والحزمة لا يتغير فيها إلا سطر السر بترميز Windows-1256 وCRLF، وأكواد الإصدار غير أكواد التطوير، و`MakeAccde.vbs`، وإعدادات الإنتاج، وخطة الرفع وترتيب `app_offline.htm` وبقاؤه بعد الفشل، وتقسيم السكربتين عند `GO`، و`TRY/CATCH` في السكربت، و`.gitignore`).
- **xUnit:** `HostingTests` (`/health` 200 ثم 503 بلا صف الإعدادات، والبيانات المحمية تُقرأ بعد إعادة تشغيل الموقع).
- **يدويًا:** `release.py check`، و`deploy_web.py check`، وفتح الموقع والدخول، ثم إعادة تشغيل الموقع من لوحة الاستضافة والتأكد أنك ما زلت داخلًا، وطلبية من تطبيق المندوب وبيع من نقطة البيع، ثم فتح ACCDE والتأكد أن محرر VBA لا يفتح الكود وأن التفعيل يقبل كود `release.py code` ويرفض كود التطوير.
